# e2e_test_spec.md — Sailor E2E Pipeline Test Specification

Cross-reference: `backend_spec.md`, `paper_overview.md`,
`paper_phase1.md`, `paper_phase2.md`, `paper_phase3.md`.

This spec defines the contract for end-to-end pipeline tests that
validate Sailor's Phase 1 → 2 → 3 using minimal, self-contained
C vulnerability targets — without real CVEs, external repositories,
or long build times.

---

## 1. Goals

```
1. Verify the full pipeline (Phase 1 → 2 → 3) produces a CONFIRMED
   verdict on a known-vulnerable input within a bounded time and
   token budget.

2. Enable isolated phase testing: run only Phase 1, only Phase 2
   (with a pre-built spec), or only Phase 3 (with a pre-built witness)
   without executing the full pipeline.

3. Cover the eight assertion template CWE classes defined in
   paper_overview.md so that each template is exercised at least once.

4. Serve as regression tests: a pipeline change that breaks any
   e2e test is a breaking change.

5. Run in CI without external network access, real CVE repositories,
   or LLM API calls (Phase 1 and Phase 3 are deterministic; Phase 2
   is the only LLM-dependent phase and has an optional mock mode).
```

Non-goals:
```
- Performance benchmarking (use the evaluation framework for that)
- Testing the frontend or backend API layer
- Reproducing real CVEs (use design/cve/ test suite for that)
```

---

## 2. Vocabulary

```
Workspace     A directory containing one test case. Named after its
              primary CWE (e.g. cwe_122/). The pipeline treats it
              as a self-contained C project.

Target        The minimal C source file(s) inside a workspace that
              contain exactly one known vulnerability. Must build
              with: clang -O1 -g target.c -o target

Ground Truth  The expected.json file that records what a correct
              pipeline run must produce, used by the test runner
              to assert correctness.

Fixture       A pre-built pipeline artifact (spec JSON, witness
              .ktest, or verified_bug.json) stored alongside the
              workspace for isolated phase testing.

Mock LLM      A test-only LLM client that returns pre-recorded
              responses instead of making real API calls.
              Used to make Phase 2 deterministic and free.
```

---

## 3. Workspace Layout

Every workspace under `tests/e2e_workspace/` MUST follow this layout:

```
tests/e2e_workspace/
└── <cwe_id>/
    ├── target.c            ← single-file vulnerable C program (required)
    ├── Makefile            ← build instructions (required)
    ├── expected.json       ← ground truth (required)
    ├── README.md           ← human explanation (required)
    └── fixtures/           ← pre-built artifacts for isolated testing
        ├── spec.json           ← Phase 1 output (VulnerabilitySpec)
        ├── witness.ktest       ← Phase 2 output (KLEE witness)
        └── verified_bug.json   ← Phase 3 output
```

The `fixtures/` directory is generated by running the full pipeline
once and committing the outputs. It is NOT manually authored.
If a pipeline change invalidates a fixture, the fixture must be
regenerated and reviewed before committing.

## 4. Target Design Rules

All targets MUST satisfy these constraints:

### 4.1 Structural constraints

```
- Single C file (target.c). No additional source files.
- No external library dependencies beyond libc.
- Compiles with: clang -O1 -g target.c -o target
  (no flags beyond -O1 -g; no -I flags needed)
- Maximum 50 lines of C code.
- Exactly one vulnerable site ℓ (one memcpy / one free / etc.)
- The vulnerability is reachable from main() in at most 3 call levels.
- No loops that KLEE must unroll more than once to reach ℓ.
```

### 4.2 Vulnerability constraints

```
- The vulnerability MUST be detectable by at least one of the
  34 CodeQL queries in the Sailor query suite (paper_phase1.md §1).
- The vulnerable site ℓ MUST be reachable via a straight-line path
  from the entry function with at most 2 guard conditions.
- The exploit condition MUST be expressible as a single symbolic
  scalar (e.g. size_t n) with two klee_assume constraints:
    klee_assume(n > SAFE_BOUND);
    klee_assume(n <= LARGE_BOUND);
- KLEE MUST produce a .ktest witness in fewer than 20 turns
  under the default budget (T_max=60).
```

### 4.3 Reproducibility constraints

```
- The ASan crash MUST be deterministic: running the replay driver
  with the same witness bytes MUST always produce the same crash.
- The crash MUST originate in target.c (not in libc internals),
  so ResultClassifier can confirm the verdict.
- The dedup_key (hash of file + func + line) MUST be stable across
  pipeline runs.
```

### 4.4 Forbidden patterns

```
- No fork(), exec(), threads, signals.
- No file I/O (fopen, read, write). Target must not access filesystem.
- No global mutable state that KLEE cannot track symbolically.
- No inline assembly.
- No VLAs (variable-length arrays on stack) — use malloc instead.
```

## 5. Target Templates

One template per CWE class. Implementations MUST match these patterns
exactly (same function names, same argument order) so that the test
runner can use the same fixture-generation script for all workspaces.

### 5.1 CWE-122: Heap-Based Buffer Overflow

```c
/* cwe_122/target.c */
#include <stdlib.h>
#include <string.h>

/*
 * Vulnerable: src_size is not checked against dst_size before memcpy.
 * CWE-122: Heap-based Buffer Overflow.
 * Detectable by: local/cpp/cwe-120-overflow (custom query).
 */
static void vulnerable(unsigned char *dst, size_t dst_size,
                        unsigned char *src, size_t src_size) {
    memcpy(dst, src, src_size);   /* ← ℓ */
}

int main(void) {
    unsigned char *dst = malloc(16);
    unsigned char *src = malloc(512);
    size_t n = 17;                /* exploit: n > 16 */
    vulnerable(dst, 16, src, n);
    free(dst);
    free(src);
    return 0;
}
```

Entry function for KLEE: `vulnerable()`
Symbolic variable: `src_size` (size_t)
Guard conditions: none (straight-line path)
Assertion template: `n <= min(len(dst), len(src))`

### 5.2 CWE-121: Stack-Based Buffer Overflow

```c
/* cwe_121/target.c */
#include <string.h>

static void vulnerable(const char *input, size_t input_len) {
    char buf[16];
    memcpy(buf, input, input_len);   /* ← ℓ */
}

int main(void) {
    char input[512];
    vulnerable(input, 17);           /* exploit: 17 > 16 */
    return 0;
}
```

Entry function for KLEE: `vulnerable()`
Symbolic variable: `input_len` (size_t)
Guard conditions: none
Assertion template: `n <= min(len(dst), len(src))`

### 5.3 CWE-416: Use-After-Free

```c
/* cwe_416/target.c */
#include <stdlib.h>
#include <string.h>

typedef struct { int value; } Item;

static int vulnerable(int trigger) {
    Item *p = malloc(sizeof(Item));
    p->value = 42;
    if (trigger) {
        free(p);           /* free */
    }
    return p->value;       /* ← ℓ  use-after-free when trigger != 0 */
}

int main(void) {
    return vulnerable(1);  /* exploit: trigger = 1 */
}
```

Entry function for KLEE: `vulnerable()`
Symbolic variable: `trigger` (int)
Guard conditions: `if (trigger)` — one guard
Assertion template: `no use of p after free(p)`
Note: free() stub MUST call real free() per paper_phase2.md §4.2

### 5.4 CWE-476: Null Pointer Dereference

```c
/* cwe_476/target.c */
#include <stdlib.h>

typedef struct { int x; } Node;

static int vulnerable(Node *p) {
    return p->x;           /* ← ℓ  null deref when p == NULL */
}

int main(void) {
    return vulnerable(NULL);   /* exploit: p = NULL */
}
```

Entry function for KLEE: `vulnerable()`
Symbolic variable: `p` (Node*)
Guard conditions: none
Assertion template: `p != NULL before *p`

### 5.5 CWE-190: Integer Overflow

```c
/* cwe_190/target.c */
#include <stdlib.h>
#include <stdint.h>

static void *vulnerable(uint32_t count, uint32_t item_size) {
    uint32_t total = count * item_size;   /* ← ℓ  overflow */
    return malloc(total);
}

int main(void) {
    return vulnerable(0x80000001u, 4u) == NULL ? 1 : 0;
    /* exploit: 0x80000001 * 4 = 4 (wraps), malloc(4) succeeds,
       but caller expects count * item_size bytes */
}
```

Entry function for KLEE: `vulnerable()`
Symbolic variables: `count`, `item_size` (uint32_t)
Guard conditions: none
Assertion template: `arithmetic within type range`

## 6. expected.json Schema

Every workspace MUST contain an `expected.json` with this schema.
The test runner validates pipeline output against it.

```json
{
  "id": "E2E-CWE-122",
  "cwe": "CWE-122",
  "description": "Heap-based buffer overflow via unchecked memcpy size",

  "target": {
    "file": "target.c",
    "func": "vulnerable",
    "line": 9
  },

  "phase1": {
    "must_detect": true,
    "expected_rule_id": "local/cpp/cwe-120-overflow",
    "expected_assertion_template": "n <= min(len(dst), len(src))",
    "min_findings": 1
  },

  "phase2": {
    "expected_outcome": "bug_triggered",
    "max_turns": 20,
    "witness_symbolic_vars": ["src_size"],
    "witness_must_violate": "src_size > 16"
  },

  "phase3": {
    "expected_verdict": "CONFIRMED",
    "expected_asan_type": "heap-buffer-overflow",
    "crash_must_be_in_file": "target.c"
  },

  "performance": {
    "max_wall_seconds": 120,
    "max_llm_tokens": 50000,
    "max_klee_paths": 500
  }
}
```

Field semantics:

```
phase1.must_detect         if true, test FAILS if Phase 1 finds no spec
                           at target.file:target.func
phase2.max_turns           test FAILS if bug_triggered not reached within
                           this many turns (regardless of T_max)
phase2.witness_symbolic_vars  all named vars must appear in .ktest
phase3.crash_must_be_in_file  ResultClassifier must find a stack frame
                           in this file for CONFIRMED verdict
performance.*              soft limits: test WARNS but does not FAIL
```

## 7. Test Runner Contract

The test runner (`tests/e2e_self_test.py`) MUST implement these modes:

### 7.1 Full pipeline test

```
Input:  workspace directory path
Steps:  Phase1Pipeline → Phase2Pipeline → Phase3Pipeline
        (all running inside DockerRunner per CLAUDE_infra.md)
Assert: compare output against expected.json
Output: PASS | FAIL with diff against expected.json
```

### 7.2 Phase 1 only

```
Input:  workspace directory path
Steps:  Phase1Pipeline only
Assert: phase1 fields in expected.json
Output: PASS | FAIL
        also writes fixtures/spec.json for use by Phase 2 only test
```

### 7.3 Phase 2 only

```
Input:  workspace directory path + fixtures/spec.json
Precondition: fixtures/spec.json must exist
Steps:  Phase2Pipeline only, using the pre-built spec
Assert: phase2 fields in expected.json
Output: PASS | FAIL
        also writes fixtures/witness.ktest
```

### 7.4 Phase 3 only

```
Input:  workspace directory path + fixtures/witness.ktest
Precondition: fixtures/witness.ktest must exist
Steps:  Phase3Pipeline only, using the pre-built witness
Assert: phase3 fields in expected.json
Output: PASS | FAIL
        also writes fixtures/verified_bug.json
```

### 7.5 Mock LLM mode (Phase 2 without real API calls)

```
Trigger: environment variable E2E_MOCK_LLM=true

Behavior:
  Phase 2 uses a MockLLMClient instead of GeminiClient or AnthropicClient.
  MockLLMClient reads pre-recorded responses from:
    fixtures/mock_llm_turns/<turn_number>.json
  Each file contains: { "prompt_hash": ..., "response": ... }
  If prompt_hash matches → return recorded response.
  If no match → raise MockLLMError (test fails with diagnostic).

Purpose:
  Run Phase 2 in CI without GEMINI_API_KEY or ANTHROPIC_API_KEY.
  Fixture generation (recording) requires a real LLM run once;
  subsequent CI runs are free and deterministic.

Recording mode: E2E_MOCK_LLM=record
  Runs real LLM, saves responses to fixtures/mock_llm_turns/.
  Must be run manually and outputs committed to the repository.
```

## 9. CI Integration

```
Test commands:

# Full pipeline for all workspaces (slow, requires Docker + LLM)
pytest tests/e2e_self_test.py -m e2e_full -v

# Phase 1 only for all workspaces (fast, no LLM)
pytest tests/e2e_self_test.py -m e2e_phase1 -v

# Phase 2 mock mode for all workspaces (fast, no LLM, no Docker for LLM)
E2E_MOCK_LLM=true pytest tests/e2e_self_test.py -m e2e_phase2 -v

# Single workspace
pytest tests/e2e_self_test.py -k cwe_122 -v

# Phase 3 only for all workspaces (fast, no LLM)
pytest tests/e2e_self_test.py -m e2e_phase3 -v

CI pipeline recommendation:
  PR gate:   e2e_phase1 + e2e_phase2 (mock) + e2e_phase3  → fast, free
  Nightly:   e2e_full on cwe_122 only                      → real LLM, ~2 min
  Weekly:    e2e_full on all workspaces                    → real LLM, ~10 min
```

## 10. Fixture Regeneration Policy

```
When to regenerate fixtures:
  - sailor/ pipeline code changes that affect Phase 1/2/3 output
  - Target C file changes
  - Assertion template changes

How to regenerate:
  E2E_MOCK_LLM=record pytest tests/e2e_self_test.py -k cwe_122 --full
  → runs real pipeline, overwrites fixtures/

Review requirement:
  - Any fixture change requires human review before merge.
  - CI blocks on fixture changes without a "fixtures-reviewed" label.
  - Reason: fixtures encode the expected correct behavior of the pipeline;
    auto-accepting fixture changes would defeat the regression test purpose.
```

## 11. Open Questions

```
1. Docker isolation for e2e tests.
   Each workspace test creates a DockerRunner. In CI, Docker-in-Docker
   or a pre-warmed runner pool may be needed. Confirm CI environment.

2. Mock LLM prompt stability.
   If LLM prompts change (e.g. new driver rules), all mock fixtures
   must be re-recorded. Consider a prompt-hash-based invalidation
   mechanism to detect stale fixtures early.

3. Parallel workspace execution.
   Running all workspaces in parallel requires multiple Docker runners.
   With 4 workspaces × ~2 min each, sequential is ~8 min; parallel is ~2 min.
   Tradeoff: resource usage vs CI latency.

4. Coverage of all 34 queries.
   The initial workspace set exercises 5 of 34 queries.
   Define a policy for when additional workspaces must be added
   (e.g. when a new custom query is added to the suite).
```
