# paper_phase3.md — Sailor Phase 3: Concrete Validation

---

## Phase 3 Overview

```
Input:  .ktest witness files from Phase 2 (only bug_triggered outcomes)

Output: per spec:
  CONFIRMED       → verified_bug.json + concrete replay driver
                    + ASan crash report
  not_confirmed   → discarded (not counted toward final tally)

Process: run AddressSanitizer against the UNMODIFIED project source
         using witness bytes from .ktest as concrete inputs.
```

Phase 2 harness H is simplified (type-level stubs, branch/loop
reductions, function stubs). H may trigger an error that the real
code would not. Phase 3 replays against the real `.a` to filter
those out.

---

## Three-Step Process

### Step 1: Symbolic Driver → Concrete Replay Driver

Transform the Phase 2 driver:

```
klee_make_symbolic(p, n, name)  → memcpy(p, <bytes from .ktest>, n)
klee_assume(...)                → remove
klee_assert(...)                → remove
klee_warning_once(...)          → remove
#include <klee/klee.h>          → remove
                                  add #include <string.h>
```

Example transformation:
```c
// Phase 2 Symbolic Driver:
size_t sz;
klee_make_symbolic(&sz, sizeof(sz), "copy_size");

// Phase 3 Concrete Replay Driver:
size_t sz;
memcpy(&sz, "\x11\x00\x00\x00\x00\x00\x00\x00", sizeof(sz));
// copy_size = 17  (witness value from .ktest, little-endian)
```

### Step 2: Compile Unmodified Project with ASan

Re-invoke the project's normal build with ASan flags injected,
producing an ASan-instrumented `.a` archive. Link the replay
driver against that `.a`.

```bash
# Re-build project with ASan instrumentation:
CFLAGS="-fsanitize=address -O1 -g" \
CXXFLAGS="-fsanitize=address -O1 -g" \
LDFLAGS="-fsanitize=address" \
<project's normal build command>
# → produces ASan-instrumented libXXX.a (UNMODIFIED project source)

# Link replay driver against instrumented archive:
clang -fsanitize=address -O1 -g \
      replay_driver.c \
      libXXX.a \
      -o reproducer
```

The `.a` MUST be built from the unmodified project source.
NEVER compile the LLM-generated code slice or stubs into the `.a` —
that would only confirm harness behavior, not the real vulnerability.

### Step 3: Execute and Classify

```
Run: ASAN_OPTIONS=halt_on_error=1:print_stacktrace=1 ./reproducer

CONFIRMED conditions (ALL must hold):
  1. ASan reports a memory safety violation
     ("ERROR: AddressSanitizer: ..." in stderr)
  2. At least one ASan stack frame points inside the project's
     own source files (i.e., into the unmodified .a)

NOT CONFIRMED (any of):
  - No crash
  - Crash occurs only in harness/replay-driver code
  - ASan output present but no project source in stack trace
```

## Stack-Frame Origin Check

Used to decide whether an ASan stack frame counts as "inside the project":

```python
def frame_is_in_project(frame_file: str, project_root: str,
                        harness_files: set[str]) -> bool:
    """True iff the ASan stack frame lives inside the project's
    unmodified source (NOT harness code, NOT system libraries)."""
    if any(frame_file.endswith(h) for h in harness_files):
        return False                                  # reject harness frame
    if frame_file.startswith(("/usr/", "/lib/", "/include/")):
        return False                                  # reject system frame
    return project_root in frame_file
```

`harness_files` covers driver.c, stubs.c, slice.c, replay_driver.c —
any file generated by Phase 2.

## Three-Phase Classification

ASan verdict is ground truth (produced from unmodified source).

```
Phase 1 → CodeQL → CWE-level pattern
  "CWE-120: Buffer Overflow via memcpy (unchecked length)"

Phase 2 → KLEE   → Memory error type (.ptr.err / .free.err)
  ".ptr.err: memcpy OOB write, copy_size=17 > 16-byte dst"

Phase 3 → ASan   → Concrete violation
  "heap-buffer-overflow: READ of size 8"
```

ASan crash type → final CWE in verified_bug.json:

```
ASan "heap-buffer-overflow"   → CWE-122
ASan "stack-buffer-overflow"  → CWE-121
ASan "global-buffer-overflow" → CWE-787
ASan "heap-use-after-free"    → CWE-416
ASan "double-free"            → CWE-415
```

## .ktest Witness Parsing

Witness bytes are read from KLEE's `.ktest` files. The format belongs
to KLEE — do not reimplement it. Use one of:

- KLEE's `ktest-tool` CLI to dump witness bytes as text/hex
- KLEE's `KTest_fromFile` C API
- Existing Python parsers in the KLEE repository

Each `.ktest` contains a sequence of (name, bytes) objects, one per
`klee_make_symbolic` call in the Phase 2 driver. Names match the
third argument of `klee_make_symbolic`. Bytes are little-endian on
x86_64 hosts.

```
  on addr 0x502000000018

  #0 _bfd_x86_elf_late_size_sections()  elfxx-x86.c:2286

SUMMARY: heap-buffer-overflow elfxx-x86.c:2286
```

Note: ASan reports line 2286; the original CodeQL spec reports
line 2699. Both locate the same memcpy call in
`_bfd_x86_elf_late_size_sections`; the difference is how each tool
maps the instruction back to source coordinates.

### Replay Driver

```c
int main() {
  bfd *out = calloc(1, sizeof(bfd));
  // ... setup identical in shape to the Phase 2 driver,
  //     but with klee_make_symbolic replaced by memcpy of witness bytes
  //     and all klee_* helpers stripped ...

  // Witness: copy_size = 17 (from .ktest)
  memcpy(&sz, "\x11\x00\x00\x00\x00\x00\x00\x00", sizeof(sz));
  htab->plt_eh_frame->size = sz;

  _bfd_x86_elf_late_size_sections(out, info);
}
```
